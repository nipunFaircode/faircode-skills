01Why we're doing this

Our delivery pipeline leaks quality at predictable points. This suite turns the way we work into explicit, repeatable steps — with guard-rails strong enough for a growing, still-maturing team — so delivery becomes quality, predictable and market-presentable.

DiscoveryConsultants miss points during customer discussions; long written notes leave everyone guessing.
HandoffTasks reach developers without clear acceptance criteria; requirements get misunderstood.
DevelopmentCode copy-pasted from chat, Frappe methods ignored, simple problems over-engineered.
TestingNo consistent Frappe TDD or end-to-end tests; quality isn't enforced by CI/CD.

Each skill below targets one of these leaks, and the CI guard-rails make the most important standards non-optional — they hold regardless of who (or what) wrote the work.

02The core idea

A skill is a short, focused playbook. Some are run by an AI assistant while coding (TDD, Frappe methods); some are human checklists (UAT, customer comms); many are hybrid. They share one vocabulary and chain together across the project lifecycle, so an inexperienced team member is never guessing what to do next.

The principle: Skills advise; CI enforces. We document the right way to work, and then we wire the few things that truly matter (tests, coverage, review) so they can't be skipped.

It extends the official frappe/skills repo (which covers code style and app dev) into the delivery and process side they don't cover.

05Interactive discovery & the coverage gate

This is the direct fix for our #1 pain — consultants missing points. The discovery and documentation skills are interviewers, not forms.

How it behaves

  • Asks one question at a time, module by module — never dumps a long form.
  • Driven by the ERP Coverage Map: every item is marked answered, N/A (with reason), or open.
  • Hard gate: no solution, blueprint, or final docs while any in-scope item is still open.
  • Two modes: an internal consultant-readiness interview, and a customer-facing one with visual cues.

The ERP Coverage Map

Selling · Buying · Stock · Manufacturing · Accounts/Finance · HR & Payroll · Projects · CRM · Assets · Quality · Support · Website/Portal · Company structure · Chart of accounts · Taxes · Naming series · Roles & permissions · Workflows & approvals · Print formats · Integrations · Data-migration sources · Reporting/KPIs · Multi-company/currency · Localisation
Why it matters: "We've covered the main things, let's design" is exactly how points get missed. The gate forces every relevant area to be explicitly answered or ruled out — on the record — before we commit to a solution.

06How it's built

Packaged as a Claude plugin

A single git repo with a plugin manifest, so the whole team installs the same source of truth with one command and gets updates as we improve it.

One ERPNext helper, shared

A small client that reads Projects/Tasks/ToDos and safely writes back (creates tasks, logs MoM action items, files bugs) — but always prints the payload and asks for confirmation first. Token comes from an environment variable, never the code.

07How quality gets locked

Two layers. The first guides; the second enforces.

① Skill layer — advisory

Guard-rail skills carry a mandatory checklist, a "STOP / red-flags" table (catching rationalisations like "let me just copy this from chat"), and a Definition of Done the work is checked against.

② CI layer — the real lock

Ready-to-drop pipelines for both GitHub Actions and GitLab CI: lint → Frappe tests → coverage threshold. With branch protection, nothing reaches main without green checks — no matter who wrote it.

Net effect: sloppy or misunderstood work is caught before it ships to a customer, which is exactly the predictability we're after.

08Rollout plan

We're not dropping 24 skills on the team at once. We pilot the highest-impact ones, prove them, then expand.

Phase 1 — Pilot DONE

Router (faircode-help, faircode-delivery), interactive requirements-discovery, task-breakdown, Frappe development, TDD, CI guard-rails, plus the shared ERPNext helper and references. Built and in the repo.

Phase 2 — Design & comms

solution-blueprint, customer-communication, meeting-minutes, change-request.

Phase 3 — Full testing & dev hygiene

unit / integration / browser / manual testing, git-workflow, bug-reporting, code-style.

Phase 4 — Release & governance

project-kickoff, data-migration, deployment-release, documentation-handover, project-tracking, estimation.

09Open decisions for discussion

Two small calls we'd like the team's input on:

1. CI coverage threshold. The pipelines currently fail a build under 70% test coverage. Is 70% the right bar to start with, or should we ramp (e.g. 50% now → 70% later) so early adoption isn't blocked?

2. ERPNext URL default. The helper defaults to https://erp.faircode.co when the environment variable is unset. Convenient, but it means an unconfigured run points at production (reads are safe; writes always ask first). Keep the default, or require the variable explicitly?

Security to-do (unrelated to this repo): the legacy tracker/fetch.py script had a hard-coded ERPNext API token. It should be rotated and moved to an environment variable. Treat the old token as compromised.
